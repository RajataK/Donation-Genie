# Feature Specification: Full-Stack Project Boilerplate

**Feature Branch**: `001-init-project-boilerplate`
**Created**: 2026-02-26
**Status**: Draft
**Input**: User description: "Create a full-stack boilerplate project for Donation Genie — an AI-powered donation companion app. The project should include: a frontend SPA, a backend API server, a database with migrations/seed support, and full Docker Compose orchestration so everything runs locally with a single command. Include a reverse proxy/API gateway in front of the services. The backend should have a clean layered architecture (routes, services, repositories) and expose a REST API with health-check endpoints. The frontend should have routing, a component library structure, and API client scaffolding already wired up. Add environment-based configuration so services can later target AWS (RDS, S3, ECS) without structural changes. Include a Makefile or task runner with commands for setup, dev, test, and teardown. The repo should follow a monorepo layout with shared types/contracts between frontend and backend."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Run the Entire Stack Locally (Priority: P1)

A developer clones the repository and wants to start all services
(frontend, backend, database, reverse proxy) with a single command.
After running the command, the developer opens a browser and sees the
frontend application served through the reverse proxy, with the
backend API reachable at a well-known path. The database is running
with initial seed data loaded.

**Why this priority**: Nothing else can be developed or tested until
the local environment works end-to-end. This is the foundational
developer experience that everything else depends on.

**Independent Test**: Can be fully tested by cloning the repo,
running the setup command, and verifying all services respond at
their expected URLs. Delivers a working local development
environment.

**Acceptance Scenarios**:

1. **Given** a fresh clone of the repository with required
   container runtime installed, **When** the developer runs the
   single setup/start command, **Then** all services start
   successfully and the frontend is accessible in a browser
   through the reverse proxy.
2. **Given** all services are running, **When** the developer
   visits the frontend URL, **Then** the application loads and
   can communicate with the backend API through the reverse proxy.
3. **Given** all services are running, **When** the developer
   hits the backend health-check endpoint, **Then** a successful
   status response is returned including database connectivity
   status.
4. **Given** all services are running, **When** the developer
   runs the teardown command, **Then** all services stop and
   resources are cleaned up.

---

### User Story 2 - Develop Backend Features with Layered Architecture (Priority: P2)

A developer wants to add a new backend feature (e.g., a new REST
endpoint). The project structure guides them to place route
definitions, business logic, and data access code in clearly
separated layers. Shared type definitions between frontend and
backend are available in a common location. Tests can be run in
isolation for the backend.

**Why this priority**: The backend is the core of the application
where business logic and data management live. A clean layered
structure prevents coupling and supports TDD from day one.

**Independent Test**: Can be tested by creating a new endpoint
following the layered pattern, running backend tests, and verifying
the endpoint responds correctly via the API.

**Acceptance Scenarios**:

1. **Given** the project structure exists, **When** a developer
   looks at the backend code, **Then** routes, services, and
   repositories are in clearly separated directories with obvious
   purpose.
2. **Given** the layered backend structure, **When** a developer
   adds a new endpoint, **Then** they create files in the routes,
   services, and repositories layers following existing patterns.
3. **Given** the backend is running, **When** a developer calls
   the REST API health-check endpoint, **Then** it returns a
   structured response with service status and database
   connectivity.
4. **Given** the OpenAPI schema is generated by the backend,
   **When** a developer modifies a backend API endpoint or its
   data shape, **Then** regenerating the frontend client produces
   updated TypeScript types matching the new contract.

---

### User Story 3 - Develop Frontend Features with Component Structure (Priority: P3)

A developer wants to build a new page in the frontend SPA. The
project provides a routing setup, a component library structure for
reusable UI elements, and an API client already configured to
communicate with the backend. The developer can work on the frontend
independently and run frontend-specific tests.

**Why this priority**: The frontend enables the user-facing
experience but depends on the backend API contracts being defined
first. Component structure and API client wiring accelerate
future feature development.

**Independent Test**: Can be tested by adding a new route and page
component, verifying it renders in the browser, and confirming the
API client can make requests to the backend.

**Acceptance Scenarios**:

1. **Given** the frontend project structure, **When** a developer
   looks at the codebase, **Then** they see a clear separation of
   pages/routes, reusable components, and API client modules.
2. **Given** the routing setup, **When** a developer adds a new
   route and page component, **Then** it is accessible via
   browser navigation without modifying infrastructure code.
3. **Given** the API client scaffolding, **When** a developer
   calls a backend endpoint from the frontend, **Then** the
   request is routed through the reverse proxy to the backend
   and returns a response.
4. **Given** the component library structure, **When** a developer
   creates a new reusable component, **Then** it follows the
   established pattern and can be imported by any page.

---

### User Story 4 - Run Tests Across the Monorepo (Priority: P4)

A developer wants to run tests for the entire project or for a
specific package (frontend, backend, shared). A single command runs
all tests. Individual package tests can also be run in isolation.

**Why this priority**: Testing infrastructure supports the TDD
workflow mandated by the project constitution. Without it,
developers cannot verify correctness during development.

**Independent Test**: Can be tested by running the test command and
verifying it discovers and executes tests across all packages, with
clear pass/fail output.

**Acceptance Scenarios**:

1. **Given** the project with test infrastructure configured,
   **When** a developer runs the monorepo-wide test command,
   **Then** tests for all packages (frontend, backend, shared)
   are discovered and executed.
2. **Given** individual package test support, **When** a developer
   runs tests for only the backend, **Then** only backend tests
   execute without requiring other services.
3. **Given** a failing test, **When** a developer runs the test
   suite, **Then** the output clearly identifies which test
   failed, in which package, with a meaningful error message.

---

### User Story 5 - Configure for Different Environments (Priority: P5)

A developer or operator wants to configure services for different
deployment targets (local development, staging, production). The
configuration system uses environment variables so that switching
from local services to cloud-managed equivalents (e.g., managed
database, object storage, container hosting) requires only
configuration changes, not code or structural changes.

**Why this priority**: Environment configuration is essential for
deployment but is not blocking local development. The structure
must be in place early to avoid retrofitting, but the actual cloud
values are not needed until deployment.

**Independent Test**: Can be tested by verifying that environment
variable files exist for different environments, that services
read configuration from environment variables, and that switching
configuration values changes service behavior (e.g., database
connection target).

**Acceptance Scenarios**:

1. **Given** the configuration system, **When** a developer
   inspects environment files, **Then** they see clearly
   documented variables for each service with sensible local
   defaults.
2. **Given** local default configuration, **When** the developer
   starts the stack without modifying any configuration, **Then**
   all services connect to local infrastructure (local database,
   local storage).
3. **Given** a cloud-targeted configuration, **When** environment
   variables are set to point to managed services (e.g., a
   managed database URL), **Then** the application connects to
   those services without any code changes.

### Edge Cases

- What happens when a required port is already in use on the
  developer's machine? The system MUST report a clear error
  identifying the conflicting port.
- What happens when the database container starts before
  migrations have run? The orchestration MUST ensure migrations
  complete before the backend begins accepting requests.
- What happens when a developer runs the setup command a second
  time while services are already running? The system MUST handle
  this gracefully (either restarting or reporting current status).
- What happens when a shared type is malformed or has a syntax
  error? Both frontend and backend build processes MUST report the
  error clearly with a reference to the shared package.

## Clarifications

### Session 2026-02-26

- Q: How should types/contracts be shared between Django (Python) and React (TypeScript)? → A: OpenAPI schema — Django generates the schema, TypeScript types and API client are auto-generated from it.
- Q: How should Django's project structure map to the layered architecture? → A: Django apps with explicit layers — urls.py (routes), services.py (business logic), models.py (repositories/data access).
- Q: What tool should bootstrap the React frontend? → A: Vite with React + TypeScript template.
- Q: What routing library for the frontend? → A: TanStack Router (replaces React Router v7) for type-safe file-based routing.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The repository MUST follow a monorepo layout with
  separate packages for frontend, backend, and shared
  types/contracts.
- **FR-002**: The backend MUST generate an OpenAPI schema from its
  API definitions. The frontend MUST auto-generate TypeScript types
  and an API client from that schema. This is the contract-sharing
  mechanism between Python and TypeScript.
- **FR-003**: The backend MUST expose a REST API with at minimum
  a health-check endpoint that reports service and database status.
- **FR-004**: The backend MUST follow a layered architecture within
  Django apps: urls.py for routing, services.py for business logic
  (pure functions where possible), and models.py for data access.
  Views act as thin adapters between HTTP and the service layer.
- **FR-005**: The frontend MUST be a single-page application with
  client-side routing, a component library directory structure,
  and a pre-configured API client for backend communication.
- **FR-006**: The project MUST include container orchestration
  configuration that starts all services (frontend, backend,
  database, reverse proxy) with a single command.
- **FR-007**: The reverse proxy MUST route frontend and API
  requests to the appropriate service, serving as the single
  entry point for the application.
- **FR-008**: The database MUST support migrations (schema version
  control) and seed data loading for local development.
- **FR-009**: The project MUST include a task runner or Makefile
  with commands for: initial setup, starting development
  environment, running tests, and tearing down services.
- **FR-010**: All services MUST read configuration from
  environment variables, with local development defaults provided
  in environment files.
- **FR-011**: The environment configuration structure MUST support
  cloud-managed service targets (managed database, object storage,
  container hosting) without requiring code or structural changes.
- **FR-012**: The frontend and backend MUST each have their own
  test configuration that can run independently.
- **FR-013**: A monorepo-wide test command MUST discover and run
  tests across all packages.
- **FR-014**: The backend MUST use Python with Django as the web
  framework, following Django's project conventions adapted to
  the layered architecture (routes, services, repositories).
- **FR-015**: The frontend MUST use React bootstrapped with Vite
  and TypeScript, with client-side routing, a component library
  directory structure, and functional component patterns using
  hooks.

### Key Entities

- **Service**: A deployable unit in the stack (frontend, backend,
  database, reverse proxy). Each service has a name, container
  configuration, exposed ports, health-check definition, and
  environment variables.
- **Shared Contract**: An OpenAPI schema generated by the backend
  that describes the shape of data exchanged between frontend and
  backend. The frontend auto-generates TypeScript types and an API
  client from this schema.
- **Migration**: A versioned database schema change. Each
  migration has a sequence number, description, up-operation,
  and down-operation (rollback).
- **Environment Configuration**: A set of key-value pairs that
  control service behavior. Each configuration has an environment
  name (local, staging, production), variable names, default
  values, and descriptions.

## Assumptions

- Developers have a container runtime (Docker or compatible)
  installed on their machines.
- The project targets local development as the primary use case
  for this boilerplate; cloud deployment configuration is
  structural only (no actual cloud resources are provisioned).
- The seed data is minimal placeholder data for development, not
  production data.
- The reverse proxy handles routing only; authentication,
  rate-limiting, and SSL termination are out of scope for the
  boilerplate.
- The database is relational (assumed PostgreSQL as the standard
  default for full-stack applications with migrations support).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A new developer can clone the repository and have
  all services running locally within 5 minutes (excluding
  initial container image downloads).
- **SC-002**: The health-check endpoint returns a successful
  response within 2 seconds of the stack being reported as ready.
- **SC-003**: All boilerplate tests pass on a clean setup with
  zero configuration changes from the developer.
- **SC-004**: A developer can add a new backend endpoint
  following the layered pattern without modifying any
  infrastructure or configuration files.
- **SC-005**: A developer can add a new frontend page/route
  without modifying any infrastructure or configuration files.
- **SC-006**: Switching the database connection from local to a
  remote target requires changing only environment variable
  values, not code.
- **SC-007**: The teardown command removes all running services
  and frees all ports within 30 seconds.
- **SC-008**: The test command executes and reports results for
  all packages within 60 seconds on an empty test suite.
