# Implementation Plan: Full-Stack Project Boilerplate

**Branch**: `001-init-project-boilerplate` | **Date**: 2026-02-26 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/001-init-project-boilerplate/spec.md`

## Summary

Create a full-stack monorepo boilerplate for Donation Genie with a
Django backend (Python 3.13, DRF, layered architecture), React
frontend (Vite, TypeScript), PostgreSQL database with migrations,
Nginx reverse proxy, and Docker Compose orchestration. OpenAPI
schema generated by Django serves as the contract-sharing mechanism,
with TypeScript types auto-generated for the frontend. A Makefile
provides commands for setup, dev, test, and teardown.

## Technical Context

**Language/Version**: Python 3.13 (backend), TypeScript 5.x (frontend), Node.js 24 LTS (tooling)
**Primary Dependencies**: Django 5.2 LTS, Django REST Framework 3.15, drf-spectacular, React 19, Vite 6, TanStack Router, openapi-typescript, openapi-fetch
**Storage**: PostgreSQL 17
**Testing**: pytest + pytest-django (backend), Vitest + React Testing Library (frontend)
**Target Platform**: Docker containers (local dev), AWS ECS (production target)
**Project Type**: Full-stack web application (monorepo)
**Performance Goals**: SC-001: 5 min setup, SC-002: 2 sec health-check response
**Constraints**: Single-command startup, environment-based config, no cloud provisioning
**Scale/Scope**: Boilerplate scaffold — minimal initial code, extensible structure

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

### I. Test-Driven Development (NON-NEGOTIABLE)

- **Status**: PASS
- pytest + pytest-django configured for backend with tests/ directory.
- Vitest + React Testing Library configured for frontend.
- Makefile provides `make test`, `make test-backend`, `make test-frontend`.
- Boilerplate includes example health-check test to validate TDD setup.

### II. Functional Programming First

- **Status**: PASS
- Backend: services.py contains pure functions for business logic.
  Views are thin adapters (imperative shell). Models handle data
  access at the boundary.
- Frontend: React functional components with hooks. No class
  components. Utility functions are pure.
- Shared: openapi-typescript generates type definitions, not
  runtime code.

### III. Simplicity & YAGNI

- **Status**: PASS
- Only infrastructure required by the spec is included.
- No authentication, no admin customization, no CI/CD pipeline.
- Single health-check endpoint as the example — minimal but
  sufficient to prove the stack works.
- **Justified complexity**: Reverse proxy is required by spec for
  unified entry point. Docker Compose is required for single-
  command orchestration.

### IV. Clear Boundaries & Modularity

- **Status**: PASS
- Monorepo with separate directories: backend/, frontend/, nginx/.
- Backend layered architecture: urls.py → views.py → services.py
  → models.py. One-directional dependency flow.
- Frontend: pages → components → api/types. No circular imports.
- Contract sharing via OpenAPI schema (no direct code imports
  between Python and TypeScript).

### V. Incremental Delivery

- **Status**: PASS
- User stories are independently deliverable (P1 → P5).
- Each Makefile target works independently.
- New Django apps can be added without modifying existing
  infrastructure.

### Post-Design Re-check

All gates still pass after Phase 1 design. No violations.

**Structure Decision**: Web application layout (Option 2) with
backend/ and frontend/ at the repository root. Nginx serves as the
reverse proxy and is configured via a separate nginx/ directory.
Shared types flow via OpenAPI schema (backend generates → frontend
consumes) rather than a shared code package, since Python and
TypeScript cannot share source code.
